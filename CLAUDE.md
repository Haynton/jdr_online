# CLAUDE.md

Contexte et règles pour Claude Code sur le projet Fumble Quest, application de JDR en ligne (projet de fin de formation Le Wagon).

> **Ce fichier n'est modifié que par Anthony (`Haynton` sur GitHub), ou par son agent à sa demande.** Un agent qui travaille pour un autre membre de l'équipe (voir `git config user.name` et `gh api user --jq .login`) ne le modifie pas, même pour noter une décision : il écrit ce qu'il faudrait y changer dans la description de sa Pull Request, et Anthony le reporte. La CI refuse une Pull Request d'un autre auteur qui modifie ce fichier (job `claude_md_owner`, `.github/workflows/ci.yml`).

## Le projet

Application web pour jouer à des jeux de rôle entre amis, en ligne ou en suivant une partie en cours autour d'une table : comptes, tables de jeu, fiches de personnage, lancer de dés, chat et fil de jeu en temps réel, plateau interactif, éditeur de carte, fonctions IA (résumé de séance, mémoire de campagne, fiche en langage naturel, commande /action), visio Jitsi.

Projet réalisé en deux semaines, en équipe de deux ou trois personnes. Les membres de l'équipe sont en formation : le code doit pouvoir être relu, compris et expliqué par la personne qui ouvre la Pull Request.

## Comment travailler avec moi

- Répondre toujours en français. Le code, les noms de branches et les messages de commit restent en anglais
- Avant de modifier des fichiers, annoncer brièvement ce qui va être fait et pourquoi
- Après chaque modification, expliquer ce qui a changé, fichier par fichier, avec des mots simples
- Avancer par petites étapes vérifiables plutôt qu'en un seul gros changement

- Ne jamais présenter une commande comme réussie sans avoir lu sa sortie

## Stack

- Ruby 3.3.5, Rails 8.1
- PostgreSQL 15 en local, Heroku Postgres en production
- Pipeline d'assets : Sprockets (`sprockets-rails`), JavaScript par importmap
- Authentification : Devise (avec `:recoverable` pour le mot de passe oublié)
- Formulaires : Simple Form (sans configuration Bootstrap)
- CSS : Tailwind v4 via `tailwindcss-rails`. **Pas de Bootstrap, pas de Font Awesome**
- JavaScript : Stimulus et Turbo. Pas de jQuery
- Temps réel : Action Cable et Turbo Streams. En production : **Solid Cable** (décision du 23 novembre, conseil de la prof : aucun service en plus, PostgreSQL suffit à notre taille ; Redis écarté), dans la base principale (voir Base de données)
- Images : Active Storage avec Cloudinary
- Variables d'environnement : `dotenv-rails` en développement, variables Heroku en production
- Hébergement : Heroku. Kamal et le Dockerfile générés par Rails ne sont pas utilisés
- Langues : I18n de Rails, français et anglais. Langue choisie par le compte, sinon par le navigateur, sinon l'anglais. Gems `rails-i18n` et `devise-i18n` (à installer, voir Prochaines tâches)
- Thème : clair, sombre ou système, avec la variante `dark` de Tailwind pilotée par une classe `.dark` sur `<html>` et des couleurs nommées (voir Couleurs et thème)

## Commandes

- Lancer l'application : `bin/dev` (serveur et reconstruction du CSS Tailwind). Une fois Tailwind installé, ne pas utiliser `rails s` seul : les classes Tailwind ne seraient pas reconstruites
- Base de données : `rails db:migrate`, `rails db:seed`
- Style Ruby : `bin/rubocop`
- Tests : `bin/rails test` (sans les tests système), `bin/rails test:system` (navigateur Chrome invisible), `bin/rails test:all` (tout)
- Console : `rails c`

## Règles de code

### Lisibilité avant tout

- Le code doit se lire comme une phrase. S'il faut un commentaire pour comprendre ce que fait une ligne, renommer ou découper plutôt que commenter
- Les commentaires expliquent le **pourquoi**, jamais le **quoi**

### Nommage

- Des noms complets et explicites, qui disent ce que contient la variable ou ce que fait la méthode
- **Interdits** : les noms d'une lettre (`i`, `x`, `e`, `t`, `u`), les abréviations obscures (`tmp`, `obj`, `val`, `res`, `arr`, `data`), les noms vagues (`stuff`, `thing`, `info`, `manager`)
- Y compris dans les blocs et les boucles : `players.each { |player| ... }`, pas `players.each { |p| ... }`
- Y compris pour les erreurs : `rescue ActiveRecord::RecordNotFound => error`, pas `=> e` (RuboCop réglé dans ce sens : `Naming/RescuedExceptionsVariableName`, `PreferredName: error`)
- Les booléens se lisent comme une question : `game_master?`, `visible_to_players?`, `isBlocked`, `hasMoved`
- Les méthodes commencent par un verbe quand elles agissent : `roll_dice`, `move_token`, `broadcast_event`
- Ruby : `snake_case` pour les variables et méthodes, `CamelCase` pour les classes
- JavaScript : `camelCase` pour les variables et fonctions, `PascalCase` pour les classes

Exemple :

```ruby
# À éviter
def calc(t, x)
  t.each { |i| x += i.v }
  x
end

# À préférer
def total_damage(dice_results, bonus)
  dice_results.sum(&:value) + bonus
end
```

### Limiter l'imbrication

- Deux niveaux d'indentation au maximum dans une méthode. Au-delà, découper
- Utiliser des clauses de garde (retour anticipé) plutôt que des `if` imbriqués
- Pas de `if` dans un `if` dans une boucle : extraire une méthode avec un nom clair
- Une méthode fait une seule chose. Viser une dizaine de lignes au maximum

Exemple :

```ruby
# À éviter
def move_token
  if current_user
    if @table.session_in_progress?
      if @token.owner == current_user
        @token.update(position_params)
      end
    end
  end
end

# À préférer
def move_token
  return head :forbidden unless @table.session_in_progress?
  return head :forbidden unless @token.owner == current_user

  @token.update(position_params)
end
```

### Ruby et Rails

- Indentation de deux espaces
- Contrôleurs minces : la logique métier va dans les modèles ou dans des services (`app/services/`)
- Un service = une classe = une action, avec une méthode `call` (ex. `DiceRoller`, `SessionSummarizer`)
- Pas de logique dans les vues ERB : la préparer dans le contrôleur, un helper ou le modèle
- Utiliser les conventions Rails (noms de tables, associations, routes `resources`) plutôt que des solutions maison
- Pas de requête en base dans une boucle (problème N+1) : utiliser `includes`
- Valider les données dans le modèle, pas seulement dans le formulaire
- Respecter `.rubocop.yml`
- **Rangement par domaine** : ce qui sert à la fiche de personnage est dans des dossiers `character_sheets/` (services `CharacterSheets::Builder`, `::Calculator`... dans `app/services/character_sheets/` ; helpers `CharacterSheets::FieldsHelper`, `::LayoutHelper`... dans `app/helpers/character_sheets/` ; vues `app/views/character_sheets/fields/`, `sections/`, `summary/`), les catalogues dans `app/services/catalogs/` (`Catalogs::Loader`), la langue dans `app/services/locales/`. Un dossier = un module Ruby (convention Rails, vérifiée par `bin/rails zeitwerk:check`). Un nouveau domaine qui grandit (plus de deux ou trois fichiers) prend son dossier ; un composant seul reste à plat (`buttons_helper.rb`)
- **Un type de champ = une classe du registre** (`app/models/field_types/`, une ligne dans `FieldTypes::ALL`) : elle dit tout de lui (paramètres demandés au MJ, partiel, groupe de mise en page et du récapitulatif, conversion, vérification, valeur de départ). Le code demande au type (`FieldTypes.of(field).convert(...)`) au lieu de décider « selon le type » ; un `when "number"` ou une liste de types dans un helper est un signe à corriger. Chercher **des champs précis** (« les caractéristiques », `field["type"] == "ability"`) reste normal
- **Une règle de calcul = une classe du registre** (`app/models/computed_rules/`, une ligne dans `ComputedRules::ALL`) **et son jumeau JavaScript** (`app/javascript/computed_rules/`, une ligne dans son `index.js`), qui font le même calcul : modifier l'un, c'est modifier l'autre. La classe dit les réglages qu'elle lit (`REQUIRED_PARAMETERS`, vérifiés par le validateur), si elle lit le dé de vie de la classe (`READS_HIT_DIE`), si la page la calcule (`LIVE`), et calcule sa valeur (`value(field, reader)`, avec `CharacterSheets::SheetReader`). Même principe pour les règles de modificateur (`ModifierRules`, `app/models/modifier_rules/` et `app/javascript/modifier_rules/`). Jamais de `case field["rule"]`
- **Une façon de jouer une règle de la table = une classe de son registre** : les points de vie des niveaux suivants (`app/models/hit_point_methods/`, `HitPointMethods::ALL` : `average`, `roll`), déclarées par le modèle dans `character_fields.hit_point_methods`, et l'équipement de départ (`app/models/starting_equipment_methods/`, `StartingEquipmentMethods::ALL` : `either`, `items_only`, `gold_only`, dans `character_fields.starting_equipment_methods`), vérifiées avec les méthodes des caractéristiques par `SheetTemplates::RuleMethodsCheck` (`RULES` : une ligne par règle). Une table range ses choix dans `rules` (`TableRules::RULE_METHODS` : une ligne par règle ; « Au choix du joueur » pour celles de `RULES_WITH_PLAYER_CHOICE`)
- **Une méthode des caractéristiques = une classe du registre** (`app/models/ability_methods/`, une ligne dans `AbilityMethods::ALL` : `roll`, `standard_array`, `point_buy`) : ses réglages (`OWN_PARAMETERS`, `REQUIRED_PARAMETERS`, `settings_errors`, vérifiés par `SheetTemplates::RuleMethodsCheck`, ex `AbilityMethodsCheck`), son guide sur l'étape Caractéristiques (`guide_partial`), si ses résultats se placent depuis la liste de chaque case (`places_results?`) et ce qu'elle refuse dans les scores tapés (`score_errors`). Le modèle liste celles qu'il propose (`character_fields.ability_methods` : `type`, `label` et `help` dans ses mots, ses réglages)
- **Un effet d'option = une classe du registre** (`app/models/choice_effects/`, une ligne dans `ChoiceEffects::ALL`, dans l'ordre du résumé des choix) : le type des champs qu'il désigne (`TARGET_TYPE`, vérifié par le validateur), ses propres vérifications (`value_errors`), ce qu'il écrit dans le résumé des choix (`facts`), ce qu'il fait à la fiche quand l'option change (`apply`), et s'il a un jumeau JavaScript appliqué pendant le choix (`LIVE`, `app/javascript/choice_effects/`). **Un comportement d'étape = une classe du registre** (`app/models/creation_step_behaviors/`, `CreationStepBehaviors::ALL`, un réglage `"chooses_…": true` de l'étape) : ses partiels du formulaire et du récapitulatif, ce qu'il garde sur son étape (`fill`) et ce qu'il retire sur les autres (`keep_offered`). Jamais de `if step.chooses_spells` dans une vue. Lire **un effet précis** (`spellcasting` dans `SpellChoices`, `hit_die` dans une règle) reste normal
- **Un nouveau réglage de champ se déclare dans son type** (`OWN_PARAMETERS`, et `REQUIRED_PARAMETERS` ou `REFERENCES` s'il le faut ; un réglage commun à tous les types dans `FieldTypes::Base::COMMON_PARAMETERS`), un nouveau réglage d'étape dans `SheetTemplates::StepsCheck::STEP_PARAMETERS` : sinon `SheetTemplateValidator` refuse le modèle qui l'emploie. S'il est de ceux qu'un MJ règle sur un modèle dupliqué (son aide, ses nombres), il entre dans `FieldParameters::TUNED`, sinon la fenêtre d'un champ ne le montre pas. Il prend aussi son **genre de saisie** dans `FieldParameters::KINDS` (et ses valeurs dans `FieldParameters::CHOICES` pour une liste fermée), son libellé et son aide dans `sheet_templates.parameters` : sinon l'éditeur ne sait pas le demander
- **Clé et libellé d'un modèle** (décision du 22 novembre, pour l'éditeur) : la **clé** (`max_hp`, nom interne : champ de formulaire, `id` de la page, clé en base, adresse d'une étape) est en `snake_case` (`SheetTemplates::Check::KEY_FORMAT`, une lettre minuscule d'abord) ; l'éditeur la fabriquera à partir du libellé (« Points de vie » → `points_de_vie`). Le **libellé** est un texte libre, dans les mots du jeu : rempli, 60 caractères au plus, sans caractère de contrôle (retour à la ligne, tabulation). Il est toujours échappé à l'affichage : **jamais de `html_safe` ni de `raw` sur un texte de modèle**. Vérifiés par le validateur, pour les champs et les étapes. **Un texte propre au jeu est écrit par le modèle**, dans sa langue (l'aide d'un champ, la règle d'un bonus), jamais dans `fr.yml` : ces fichiers gardent les textes de l'application, communs à tous les jeux
- **Un sol ou un bord d'une carte dessinée = une classe du registre et son jumeau JavaScript** : `MapFloors` (`app/models/map_floors/`, une ligne dans `MapFloors::ALL`) et `MapEdges` (`app/models/map_edges/`) disent ce qui existe (la clé, vérifiée par `MapLayoutValidator`) ; leurs jumeaux (`app/javascript/map_floors/`, `app/javascript/map_edges/`, une ligne dans leur `index.js`) disent comment ils se dessinent et ce qu'ils font à leurs bords (`wallKey`, `inkBorder`, `rocksOutside`...). Le dessin leur demande (`floorOf(clé)`, `edgeOf(clé)`) au lieu de décider « selon le sol ». Un nouveau sol : sa classe, son module, son nom dans `map_templates.floors` (fr et en) ; un test vérifie les trois
- **Un objet d'une carte = une ligne du registre et son dessin JavaScript** : `MapObjects` (`app/models/map_objects.rb`, `SIZES_BY_FAMILY` : sa clé, sa taille en cases avant d'être tourné, sa famille Mobilier, Décors ou Nature) ; son dessin dans `app/javascript/map_objects/` (un fichier par famille, même taille, vérifiée par un test), son nom dans `map_templates.objects`. Le dessin le dessine à l'encre de la carte ; `drawObject` (`map_objects/index.js`) teinte ensuite ses contours de sa propre couleur (`map_editor/object_ink.js`) : passer toujours par lui. **Une carte toute faite = un fichier** (`config/map_presets/<clé>.json`, au format d'une carte enregistrée, vérifié par un test contre `MapLayoutValidator`), sa clé dans `MapPresets::KEYS`, son nom et sa description dans `map_templates.presets`
- **Un partiel appelé par un nom construit passe par une table de correspondance**, chemins écrits en entier (`CharacterSheets::PartialsHelper::SECTION_PARTIALS`, `CharacterSheets::SummaryHelper::SUMMARY_GROUP_PARTIALS` ; le partiel d'un champ est dit par son type, `FieldTypes`) : jamais `render "dossier/section_#{layout}"`, qu'une recherche du nom de fichier ne trouverait pas

### JavaScript

- Toujours `const` par défaut, `let` seulement si la valeur change. **Jamais `var`**
- Syntaxe moderne : fonctions fléchées, déstructuration, gabarits de chaînes, `async` et `await`
- Le JavaScript vit dans des contrôleurs Stimulus (`app/javascript/controllers/`), pas dans des balises `<script>` dans les vues
- Un contrôleur Stimulus par comportement, avec des `targets` et des `values` nommés clairement
- Pas de `console.log` laissé dans le code commité

### Tailwind et vues

- Écrire les classes Tailwind en toutes lettres. **Jamais de classe construite par interpolation** (`col-start-#{x}`, `` `bg-${color}` ``) : Tailwind ne la générera pas. Pour une position calculée (jetons du plateau), utiliser un style en ligne
- Quand un groupe de classes se répète, en faire un partiel ou un helper
- Le conteneur Jitsi garde `data-turbo-permanent` et un `id` fixe : il ne doit jamais être retiré ni rechargé de la page

### Textes et traductions

- **Aucun texte affiché à l'utilisateur écrit en dur** dans une vue, un contrôleur, un modèle ou un e-mail. Toujours passer par `t(...)` et les fichiers `config/locales/fr.yml` et `config/locales/en.yml`
- Dans les vues, utiliser les clés courtes (« lazy lookup ») : `t(".title")` dans `app/views/tables/show.html.erb` cherche `fr.tables.show.title`
- Toute nouvelle clé est ajoutée **dans les deux langues** en même temps
- Les messages de validation et les noms d'attributs passent par `activerecord.attributes` et `activerecord.errors` dans les fichiers de traduction
- Dates et nombres affichés avec `l(...)` (ex. `l(session.started_at, format: :short)`), jamais avec `strftime` en dur
- Le code, les clés de traduction, les noms de variables et les commits restent en anglais
- Seule exception : la galerie de composants `/dev/components` (développement et test seulement, jamais servie en production). Outil de l'équipe, jamais vu par les joueurs : ses textes restent en anglais, écrits en dur, avec un commentaire en tête de la vue

### Composants

Construits une fois, réutilisés partout. On les voit tous, dans les deux thèmes, sur la galerie `/dev/components` (développement et test seulement).

### Sécurité et permissions

- Toute permission est vérifiée **côté serveur** (rôle MJ ou joueur, séance en cours, visibilité réservée au MJ), jamais seulement en masquant un bouton dans la vue
- Le lancer de dés est calculé par le serveur, jamais par le navigateur
- Les réponses de l'IA (JSON) sont validées par le serveur avant toute action
- Les clés d'API ne sont jamais envoyées au navigateur

## Base de données

- Ne jamais modifier une migration déjà présente sur `main` : créer une nouvelle migration
- Toujours commiter `db/schema.rb` avec la migration qui le modifie
- Conflit sur `db/schema.rb` : prendre la version de `main`, puis relancer `rails db:migrate`
- Ne jamais lancer `rails db:drop`, `db:reset` ou `db:schema:load` sans le demander d'abord
- **Une seule base en production** (méthode « Single Database Setup » de Le Wagon, décision du 23 novembre) : Heroku Postgres ne donne qu'une base (`DATABASE_URL`), alors que Rails 8 en prévoit une par gem Solid. Les tables de Solid Cable, Solid Queue et Solid Cache sont créées par trois migrations (`install_solid_cable`, `install_solid_queue`, `install_solid_cache`, recopiées de `db/*_schema.rb`, sans `force: :cascade`) et sont dans `db/schema.rb`, aussi en développement, où elles ne servent pas. Dans `config/database.yml`, les quatre connexions de production pointent vers `DATABASE_URL` ; `database_tasks: false` sur `cache`, `queue` et `cable` laisse migrations et schéma à la base principale (vérifié en local avec l'environnement de production). Quand une tâche de fond arrivera (IA), `SOLID_QUEUE_IN_PUMA=true` sur Heroku fera tourner Solid Queue dans Puma (`config/puma.rb`), sans second dyno

## Git

- Modèle GitHub Flow : `main` est protégée et toujours déployable
- Une branche par tâche, nommée `type/palier-description-courte` (ex. `feature/p2-dice-roll`, `chore/p1-heroku-setup`)
- Types : `feature`, `fix`, `refactor`, `chore`, `style`, `docs`, `hotfix`
- Commits au format Conventional Commits : `type(portée): description` à l'impératif, en anglais, moins de 70 caractères (ex. `feat(board): snap token to nearest cell on release`)
- Types de commit : `feat`, `fix`, `refactor`, `chore`, `style`, `docs`, `test`
- Petits commits cohérents. Pas de `wip`, `update` ou `fix bug`
- `git add` fichier par fichier, jamais `git add .` sans avoir vérifié `git status`
- Fusion d'une PR par un commit de fusion classique (« Create a merge commit »), **pas de « Squash and merge »** ni de « Rebase and merge » (décision validée par le référent) : l'historique garde les petits commits de la branche
- Pas d'approbation obligatoire d'un autre membre pour fusionner une PR (décision de l'équipe)
- **Interdits** : commit ou push direct sur `main`, `git push --force`, `git reset --hard`, réécriture d'un historique déjà poussé
- Toujours demander avant de commiter ou de pousser

## Fichiers sensibles

- **Ne jamais lire, afficher, modifier ni commiter** `config/master.key` et `.env`
- Toute nouvelle variable d'environnement est ajoutée, sans valeur, dans `.env.example`
- Ne jamais écrire de clé, de mot de passe ou de jeton dans le code
- Un secret publié sur GitHub (dépôt public) est considéré comme brûlé : on ne réécrit pas l'historique pour l'effacer, on ne l'utilise plus. Il faut en générer un nouveau (`bin/rails secret`) et le ranger dans les credentials chiffrés (`bin/rails credentials:edit`) ou dans une variable d'environnement. Exemple : les valeurs `config.secret_key` et `config.pepper` retirées de `config/initializers/devise.rb` restent visibles dans l'historique, sans risque car elles n'ont jamais servi
- Ne pas commiter `app/assets/builds/*` (CSS reconstruit automatiquement)

## Commandes à faire valider avant de les lancer

- Suppression de fichiers ou de dossiers (`rm`, `rm -rf`)
- Ajout ou retrait d'une gem
- Toute commande Heroku (`heroku ...`, `git push heroku`)
- Toute commande qui touche à la base autrement que `db:migrate`
